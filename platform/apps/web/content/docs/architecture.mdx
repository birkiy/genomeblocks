# Architecture

The platform is a **decoupled three-tier app with a Python sidecar**.

## The three tiers

**Frontend — Next.js 14 + MDX.** This page is one of them. Docs under `/docs/*` are pre-rendered at build time; the dashboard under `/app/*` hydrates interactive React components. One app, one domain.

**Middleware — Fastify on Node.** Owns concurrent HTTP I/O, JWT-based anonymous sessions, and the lifecycle of a per-session sandboxed directory — the "Little Drive". Every file you upload is scoped to your session and cleaned up on a TTL sweep.

**Compute — Python subprocess.** Node spawns `python -m compute.cli <job> <args>`; Python reads files from the session drive, performs the heavy lifting (pandas/numpy), and writes JSON to stdout. Node parses it and hands it back to the browser.

## Why a subprocess

It keeps the contract narrow: **file paths in, JSON on stdout**. Every compute job is independently testable from a shell, cold-start costs are paid per-request (fine for this scale), and we avoid standing up a second web framework in Python. When the load profile demands warm imports, the same contract can be re-homed behind a long-lived FastAPI service without touching the Node or browser code.

## Same-domain routing

The browser sees one origin. `next.config.mjs` declares a rewrite from `/api/*` to the orchestrator URL, so `fetch('/api/session')` from a dashboard component gets transparently proxied at the edge. No CORS, no cookie domain headaches, no second sign-in.

## Deployment

The frontend deploys to Vercel; the orchestrator + compute ship as one container to Fly.io. GitHub Actions fires each on push to `main`, keyed on the paths that changed.
