One graph, two tables

A working prototype of the notebook design. CREs, genes and the Architecture are stored as tables that share one genome and line up by row. Intra- and inter-chromosomal edges live in one sorted edge table. Every result is checked against main.

Design

Tables that line up by row

Every table shares one Genome, and the row number links the tables. Row i of the CREs is row i of the labels, of the signal cube and of every graph column. Graph edges store row numbers, so nothing needs a lookup dictionary.

The notebook structure

Loci, Genes and Architecture are plain numpy columns. Looking at one row still gives a normal Locus (a view onto the columns), so code that reads cre[i].start or loops over peaks keeps working. Classic functions such as signal() run unchanged on the new Loci and return the same cube.

Architecture

One graph, sorted into blocks

Most loops are within one chromosome, and a few cross chromosomes. Keep them all in one edge table, sorted so each chromosome's edges form one block and all trans edges form a final block. Nothing is split, but every part can be sliced out.

The edge table of the benchmark graph (120,230 edges)

Real counts from the trans benchmark: 114,367 cis edges and 5,863 trans edges (5% of loops). A per-chromosome analysis takes one block. A whole-genome analysis takes the whole table. Neither needs a copy.

Taking one chromosome

On main this is a Python loop that rebuilds a graph (389 ms for chr8). In the prototype it is a slice of the same arrays (61 µs), and edits to the slice write through to the full graph.

Per chromosome

A.chrom("chr8"), or for c, view in A.chroms(). Each block is independent, so blocks can go to separate processes.

Cis or trans only

A.cis, A.trans: slices again. Distance-decay fits use cis; trans gets its own flat expectation.

Whole graph

A.neighbors(row) uses one adjacency index over all edges, so a CRE's trans partners are always listed. A.graph() builds a graph-tool Graph from the arrays when you need real graph algorithms.

Speed

Same inputs, same outputs, every step faster. The biggest gain is add_mcool: 23 s → 295 ms. The prototype maps every edge to its Hi-C pixel with array lookups, reading pixels one chromosome block at a time, instead of one pandas lookup per edge.

Notebook

The interactive part

Scale

Bigger loop sets

The prototype runs 1,000,000 loops (1,428,862 edges) in 5.3 s. main needs 82 s for 200,000 loops; it was not run at 1M.

Trans loops

Inter-chromosomal edges

With 5% trans loops, main builds the graph and adds Hi-C, then stops at normalize (TypeError). Locus.distance_to has no distance between chromosomes, and normalize writes that missing value into a float column. The prototype gives trans edges an infinite distance and normalises them against the mean trans contact.

The synthetic Hi-C adds about 40 read pairs at each trans loop, so those edges carry real weight. The flat trans expectation is a first choice. A per-chromosome-pair expectation would be the obvious next refinement.

Try it

Using it in a notebook

import genomeblocks.columnar as gbc

cre   = gbc.Loci.make("atac.narrowPeak")          # sorted, one block per chromosome
genes = gbc.Genes.make("gencode.gtf")              # polars parse when installed
A = (gbc.Architecture.make(cre, "loops.bedpe")
       .add_mcool("hic.mcool", resolution=5000)
       .normalize().annotate(genes).strength())

A.chrom("chr8"); A.cis; A.trans                    # views, no copy
A.neighbors("chr8:127735000-127736000(.)")         # cis + trans partners
A.vp.strength[cre.row(uid)]                        # every column is aligned with cre
cube = cre.take(rows).signal(bigwigs)              # classic functions still work
g = A.graph()                                      # graph-tool for algorithms
A.save("session/arch"); gbc.Architecture.load("session/arch")

The notebook examples/columnar_prototype/columnar_prototype.ipynb on branch columnar-prototype walks through all of this with outputs: block matrix, views, trans partners, graph-tool components and PageRank, a hub signal profile, a 1,000-permutation genome-wide test, save/reload and hand-off to pandas, polars and Arrow.

Limits

What the prototype does not do yet

Classic-only features

Genes.select_isoforms, make_ucsc and the Architecture draw helpers are not ported. Use A.to_legacy() to get a classic graph for drawing.

Coolers

Fixed-size bins only. As on main, each CRE maps to the bin holding its start.

Interval kernel

The all-pairs overlap used by make scans a window as wide as the longest reference interval. That suits CREs; it would need cgranges or a tree for megabase-long intervals.

Graph-tool vertices

A.graph() has one vertex per CRE row, isolated CREs included, so vertex i is row i. Algorithms that normalise over all vertices (PageRank) are scaled differently from main's graph, which holds linked CREs only.

Edge cases kept simple

Duplicate CRE rows stay separate vertices (main merges them by uid). Ensembl-style generic "UTR" lines are classed 5' or 3' by the transcript's first CDS base. Without polars, GTF parsing falls back to pandas, which is slow (about 11 s here).

Method

How this was measured

  • Code: genomeblocks/columnar/ on branch columnar-prototype. The classic modules on that branch are byte-identical to origin/main (checked), so the in-process "main" numbers run main's code. The fresh-process runs import main from a separate checkout (ec4737a).
  • Tests: tests/test_columnar.py compares every step with the classic implementation, and the full suite passes. The benchmark repeats the comparison at full size.
  • Data: the synthetic hg38-shaped set from the benchmark report: 100k CREs, 20k genes, 50k loops (52.5k with trans), a 5 kb cooler from 5M read pairs. 4 vCPU Xeon at 2.1 GHz; medians of 3–5 runs after a warm-up (main's add_mcool: one run).
  • Bench: benchmarks/bench_prototype.py; page: benchmarks/build_prototype_report.py.
