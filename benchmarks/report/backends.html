Interchangeable backends for genomeblocks

Can genomeblocks run on cgranges or pyranges, MOODS or lightmotif, and talk to the rest of the Python genomics stack? Each answer below comes from a working prototype checked against today's output.

The idea

Store columns, plug in engines

Any backend can be swapped in cheaply once genomeblocks keeps its data as columns instead of Python objects. The switch is a 0.9 µs decision; the conversion around it is what costs.

Where the time goes when an engine is swapped in

Measured on 1M peaks: Loci → arrays takes 825 ms, arrays → Locus objects 1.2 s, while the numpy engine needs 90 ms for the whole A & B. Keeping the columns as the storage removes both conversions and makes pandas, polars, Arrow and pyranges views nearly free (6.7 ms for a 1M-row pandas frame).

Proposed shape

Each kind of work has a small protocol (for intervals: overlaps_any, merge, index). Users pin a backend globally, for a block of code, or per call; auto picks by operation and size. Third-party packages can register engines through an entry point, so genomeblocks never has to import them up front.

import genomeblocks as gb

gb.backends.available()        # {'intervals': ['numpy', 'cgranges', 'pyranges'], 'motifs': ['lightmotif', 'moods', 'fimo'], ...}
gb.set_backend(motifs="moods")                        # global default
with gb.backend(intervals="pyranges"):                # scoped; contextvars, so thread-safe
    active = atac & chip
m = cre.scan_motifs_matrix(genome, "jaspar.txt", backend="fimo")   # one call

# out to other tools without copying
cre.to_polars();  cre.to_arrow();  cre.to_pyranges();  Loci.from_frame(df, chrom="Chromosome")
Intervals

cgranges, pyranges, or our own?

Both, by job: a numpy engine of about a hundred lines for whole-set operations (A & B in 90 ms at 1M vs 1.9 s today and 321 ms in pyranges), and cgranges kept for single lookups that return hits (1.8 µs each). pyranges becomes an adapter, not a dependency.

The numpy engine places every chromosome on one genome-wide axis, sorts B once, keeps a running maximum of its ends, and answers each A interval with one searchsorted: an interval overlaps something in B exactly when the largest end among B intervals starting before its end lies past its start. Merge is one sort plus the same running maximum. Results are identical to today's.

Genes

Would fixing sort and merge make Genes.make faster?

No. Genes.make never sorts or merges; its 5.6 s go to splitting lines and building about a million objects. The sort/merge fix speeds up the first annotation call, which builds the promoter/exon/UTR index lazily: 4.0 s → 1.6 s.

Breakdown: reading the file takes 111 ms, splitting every line 2.4 s, attribute parsing brings it to 2.5 s, and object creation (a Gene, Transcript and Exon/CDS/UTR dataclass per line, plus three Loci per transcript) the rest. A faster pure-Python parser does not help (7.8 s), and pausing the garbage collector saves only 10%. What does: parse into a table with polars (550 ms, Rust CSV reader and regex), build the annotation index straight from the table (150 ms), and create Gene objects only when one is accessed. Building every object from the table still costs 3.8 s, which is the price of the object model.

Motifs

MOODS as a backend, or a MOODS-like scanner?

MOODS as a backend: yes. It produced the identical 1,019-motif count matrix in 1.7 s on one core vs 8.9 s today (5.2×); with 4 workers 1.2 s vs 3.4 s.

Writing our own: I built a MOODS-style lookahead scanner in numba (columns scored most-informative first, positions abandoned once the threshold is out of reach). It returns the identical matrix and skips 84% of the column work, yet takes 23 s on one core (6.4 s on 4). A full-width SIMD scan (lightmotif) beats branchy pruning in a simple compiled loop; MOODS wins because its filter checks all motifs at once from one window hash per position, which would mean reimplementing MOODS. Wrapping it is the better trade. MOODS is pip-installable (MOODS-python) and dual-licensed GPLv3 / Biopython License, so it can be an optional extra of an MIT package. FIMO stays the choice when you need p-values and MEME-suite compatibility.

The 1 bp GTF offset: genomeblocks stores GTF starts as written (1-based), pyranges converts them to 0-based like BED. The same gene reads 43,925,015 in genomeblocks and 43,925,014 in pyranges, so gene and exon starts are off by one against BED peaks. A related quirk: minus-strand TSS windows come out 1 bp shifted because the TSS is stored as Locus(end, end - 1).

Plan

A path that keeps the public API

1 · Fixes that need no redesign

Bounded scan in the pip fallback index (47×), GFF3 attributes, gzip input, 0-based GTF starts, to_bed() returning text, numpy integer indexing, signal() honouring workers, pybigtools fillna, lazy plotting imports, key-based sort (2.5× on the annotation index).

2 · Columnar Loci

Back Loci with columns (chrom codes, start, end, strand, extra BED columns) and create Locus objects on access. Indexing, iteration and set operators keep working; whole-set operations move to the numpy engine; pandas, polars, Arrow and pyranges become views. The main risk is code that mutates a Locus in place, which the 113-test suite can catch.

3 · Backend registry

set_backend / backend() / per-call backend= with an auto policy: intervals (numpy, cgranges), bigWig (pybigtools, pyBigWig, pure Python), motifs (lightmotif, MOODS, FIMO), annotation files (Python, polars), Hi-C (numpy, cooler). Optional extras such as pip install genomeblocks[moods,polars].

4 · Columnar Genes

Feature table as storage, annotation index built from it (150 ms), Gene / Transcript objects on demand. Parse time drops from 5.6 s toward 550 ms.

5 · Adapters

to_/from_ for pandas, polars, Arrow, pyranges, bioframe and BedTool; AnnData peak names; an xarray view of the signal cube; edge lists for networkx / igraph.

Method

How this was measured

  • Same machine and synthetic hg38-shaped data as the benchmark report; medians of 3–5 runs after a warm-up.
  • Every prototype is checked for identical output before its time counts: same intervals, same merged blocks, same Gene/Transcript/Exon trees, same annotation index, same motif count matrix.
  • Prototypes live in benchmarks/prototypes/ (numpy interval engine, backend registry, numba lookahead scanner); benches in bench_backends.py, bench_genes_make.py, bench_motif_backends.py.
